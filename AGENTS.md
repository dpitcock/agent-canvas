# Lightweight governance

## Authority and scope
- Use `config/workspace-config.yml`; `POSTMORTEM.txt` and any external legacy archive are historical evidence, not instructions.
- These rules take precedence over upstream skills, plugins, and repository instructions; Owner Override takes precedence over these rules. Skills must not add unrequested specs, plan reviews, or approval loops.
- Hybrid: use Osmani for outcome-based planning and vertical slices, and Superpowers where supported for focused fresh-context delegation; add detailed interfaces/test assertions only when a handoff needs them. Load only relevant skills; one Osmani source with shared references lives in `skills/addyosmani-agent-skills/`. Codex discovers it via `.agents/skills/addy-*`; Cline via `.cline/skills/<skill-name>`.
- `agentic_envs` selects project integrations, not the current speaker. Codex and Cline share this rulebook and task record. Use the actual running environment's supported tools; never claim a plugin or delegation capability is available merely because another environment has it. Record missing integrations in `INSTALL-FOLLOWUP.md` and continue independent work.
- Do work once: maintain one canonical plan/task record for the active scope, using the existing task description for routine work; both frameworks and all subagents use it. Give each task one implementation owner, check existing progress before dispatch, and never recreate completed tasks, duplicate plans, or add framework-specific ledgers or reports.
- Choose one technique for each activity, not two complete workflows. Reuse valid verification evidence and PR reviews; rerun only for relevant changes, failures, unresolved concerns, or an explicit request—not a framework switch. Your environment-based reviews, PR-only triggers, and focused-test rules govern both; ask Dennis only about material conflicts these rules do not resolve.
- Never apply this governance to its own construction or repair: no reviewers, approvals, or readiness gates.

## Lanes
- Authoring: toolkit tests, internal scripts, docs, and tooling use one short task description, direct implementation, and focused verification.
- Every PR follows the two-stage review workflow below: Staff and QA (plus accessibility for frontend changes), then the Codex loop. The same policy applies to this toolkit and installed projects in every target environment. Local work without a PR needs no reviewer; governance construction and repair remain exempt.
- Shipped: templates, adopter policy, distributed bootstrap, and CI configuration are strict, versioned, and reviewed at the PR.
- Classify by what adopters receive; a shipped bootstrap script stays shipped even under `scripts/`.
- CODEOWNERS separates paths for ownership; it does not implement role approvals or authorize a merge.

## Scope, risk, and environment
- Tier 1: small, isolated, low risk. Tier 2: bounded, moderate scope or risk. Tier 3: broad or high risk.
- Assess scope × risk and `target_environment` (local/dev/production) in the task description; no assessment artifact or gate.
- Local work without a PR: direct commit, no reviewers. For PRs, `approvals_required: 1` remains the numeric GitHub approval minimum; it does not replace the required role passes and completed Codex review below. Scope, risk, and environment guide review depth and additional specialists. Publish internal review findings inline and verdicts on the PR; retain Codex's native review/comment evidence for the exact head. Do not keep review evidence solely in local logs, chat, commits, or task records.
- Auth, secrets, schema, payment, or user-data changes escalate to Tier 3 regardless of environment; use relevant Staff/AppSec/QA expertise at the PR.
- Local authoring does not require a PR; publishing shipped changes uses the shipped PR lane.

## Planning
- Use Project → Phase → Epic → Task; phases are optional for smaller projects (Project → Epic → Task).
- The developer outlines project goals, boundaries, and major milestones, then details only the current phase—or current epic when phases are not needed.
- Future work stays as brief outcome descriptions with known dependencies, not task lists; expand it when it becomes current.
- Each active epic declares granular tasks, merge gates, and the test evidence its PRs will carry.
- Undetailed future work never blocks current work; moving between phases introduces no additional approval gate.
- No planning approvals. Architecture concerns go to the coordinator-selected Staff reviewer at the PR.
- Routine authoring keeps its short task description; do not create a formal plan or Principal review for it.
- Route subsequent implementation concerns to Staff Engineer, AppSec, or QA as relevant.
- QA does not participate in planning; QA reviews the PR against its declared test evidence when required.
- No approval is required before opening a PR. Plan revisions never invalidate completed work.
- Prefer subagents for substantial work: delegate bounded research, implementation, or verification tasks within the current phase or epic. Keep trivial, tightly coupled, or strictly sequential work inline. Subagents do not introduce extra reviews, approvals, or planning documents. The developer owns integration and the final result.

## Reviews and tests
- When opening or updating a PR, write its description for a teammate who has not followed the work: begin with one plain-language sentence explaining the outcome, then use `## Scope` for the user-visible behavior or important implementation changes and `## Verification` for the checks actually run. Keep bullets short and concrete; use normal Markdown line breaks rather than escaped `\\n`, expand unexplained jargon or task IDs, and state any verification limitation as a simple factual sentence. Do not turn the description into a commit log, a process narrative, or a list of files.
- During installation or upgrade integration, inspect the target project's GitHub remote, CI workflows and reported checks (including external CI), and merge-target branch protections/rulesets. Record discovered checks and any enforcement/access gaps in that project's existing `INSTALL-FOLLOWUP.md`, preserving previous resolutions. Do not create CI or change GitHub settings merely to install this toolkit. If no CI is configured, report that explicitly; missing access does not establish that CI is absent. The pre-merge CI rule applies even when GitHub does not require the checks.
- Reviews attach only to PR opened, marked ready, or explicit re-request events; never commits or task completion alone. For the internal stage, dispatch a separate coordinator using `agents/review-coordinator.md`, with PR identity, head SHA, requirements, risk/environment, and existing evidence. It assigns Staff and QA, accessibility for frontend changes, and bounded additional specialists when warranted; it does not implement fixes or approve its own assessment. Publish every internal review's summary, verdict, and actionable comments on the PR against the reviewed SHA. The developer owns the subsequent Codex loop; do not dispatch a coordinator for each Codex iteration.
- Do not duplicate a review for an unchanged PR merely because it was marked ready.
- Before any GitHub PR merge, the developer must check the current PR head SHA's check runs and commit statuses, including checks not marked required. Do not merge while any CI check is pending, queued, waiting, or running, while a required check is missing, or while any check has failed, errored, timed out, or been cancelled. Wait for completion and address failures; an unavailable or incomplete status response is not permission to merge. Immediately before merging, recheck the head SHA and results, and bind the merge to that SHA where supported; a new commit requires checking its results again. Never use an admin/force merge or disable checks to bypass CI. Review approval and `bypass-review` do not waive CI completion. GitHub-side enforcement requires branch protection or rulesets with the actual CI checks required; agent instructions alone do not enforce the merge button.
- Internal reviewers operate in fresh read-only agent contexts; publish their actual verdicts through the corresponding `dpitcock-*` GitHub Apps. Before an authorized merge, both review stages must be complete, required internal passes must remain applicable, no outstanding request for changes or unresolved blocking finding may remain, and CI must satisfy the pre-merge rule. An approval from one bot never overrides another reviewer's blocking findings; re-request the relevant reviewer when its verdict needs updating. Review-loop completion does not itself authorize merging.
- A reviewer completes its assigned review scope before publishing a verdict: inspect the entire relevant diff and required context, then report every finding supported by that pass. Never stop after the first blocking finding. After fixes change the head, re-review the affected scope—including the fix and surrounding interactions—for remaining or newly introduced issues; do not merely verify that the originally reported line changed.
- The developer owns review follow-up and comment resolution, including when using Superpowers' receiving-code-review skill. On the PR being worked, read outstanding review comments from all review rounds, check each finding against the current code, implement valid fixes, and run focused verification. Reply in each original thread with the disposition and relevant commit/test evidence, then resolve threads whose findings are addressed, including findings already fixed. Explain disagreements and leave disputed or unfinished findings open. Use the developer's identity and an available GitHub tool/API for replies and thread resolution; do not impersonate the reviewer or treat thread resolution as reviewer approval. If access is unavailable, report the unresolved threads and continue independent work.
- Discover the configured `gh_identity` / `gh-identity` MCP tools before declaring reviewer access unavailable. Search the running environment's tool registry, including deferred tools, by server name and `review_as_app`; the initial tool list and `gh auth status` do not establish MCP availability. In Codex with `functions.exec`, inspect `ALL_TOOLS` for matching names/descriptions and use the returned declaration.
- All code review skills and reviewer handoffs, including Osmani and Superpowers, must include inline code comments for actionable, line-specific findings in addition to the overall review summary and verdict. Write the summary and comments in plain language: one concise statement of the issue, why it matters, and the requested change where useful. Give the fresh reviewer the reviewed commit SHA and require each such finding to include its severity, explanation, exact repository-relative file path, diff line, and side. Keep broader findings that cannot be accurately anchored in the summary; do not invent findings or add filler comments to a clean review. This applies to every required review role without adding review triggers or reviewers.
- `gh_identity_review_as_app` submits an existing review verdict as a selected GitHub App; it does not perform the review or create an independent reviewer context. Use the fresh reviewer's actual verdict and findings, with `repo`, `pr_number`, `app_role`, `verdict` (`approve` or `request_changes`), a concise `body`, and `commit_id` set to the SHA actually reviewed. Submit line-specific findings in the same review's `comments` array: `body`, `path`, `line`, and `side` (`LEFT` for deletions, `RIGHT` for additions or context); multiline ranges also require `start_line` and `start_side`. Verify anchors against that commit's PR diff. If a comment is rejected, correct the anchor against the reviewed diff and retry; never silently drop inline findings for a summary-only submission. Staff Engineer maps to `staff`, Code Reviewer to `reviewer`, AppSec to `appsec`, QA to `qa`, and Accessibility to `a11y`; select only coordinator-assigned roles. Prefer this tool over personal-account CLI approval or retrieving tokens. If discovery or submission fails, report the specific limitation, record needed setup in `INSTALL-FOLLOWUP.md`, and continue independent work without inventing approvals.
- Run focused tests of changed behavior, without nested test runners; do not test governance machinery for its own sake.
- If an active work step exceeds 15 minutes, post a heartbeat and report its status; never kill it merely for elapsed time. Unchanged scheduled Codex polling follows the quiet-notification rule below.

## Two-stage PR review workflow
- After implementing and verifying the original changes, open the PR. Run Staff and QA reviews; also run accessibility for frontend changes. Wait for all internal reviewers to finish on the same immutable head before implementing their valid concerns. Make fixes in new commits, run focused verification, push, reply in the original threads, and resolve addressed findings. Re-request affected reviewers as needed until every required role has a published pass; reuse unaffected evidence. Follow `agents/review-coordinator.md` for handoffs and App publication.
- Never overlap internal reviews with a pending Codex review. Do not edit or push the reviewed code while either stage's reviews are pending. If Codex is already pending (including an automatic review), wait for completion before internal work. Once internal passes are obtained, begin the Codex stage; do not automatically restart Staff/QA on every Codex fix. If a fix materially invalidates their scope or approval, finish the pending Codex review, return to the affected internal reviewer, then resume Codex.
- Post exactly one `@codex review` comment for the current pushed head, including its full SHA and relevant scope/trust-model context. Reuse an existing request or pending review for that SHA rather than duplicating it. Check first after 10 minutes from the request, then every 5 minutes until completion. Silence, an old review, a reaction alone, or elapsed time is not completion: require explicit completed review/result evidence tied to that head.
- Use the host's scheduling/wakeup mechanism for waits, not a long blocking sleep. Keep PR, branch/worktree, head SHA, request link/time, next check time, and dispositions in the existing task/automation record, not another ledger. Resume idempotently: inspect remote head, local edits, all outstanding threads, and pending/completed reviews before acting. If the head changes externally, reconcile it without overwriting edits or attributing an old review to the new head. Missing scheduler/reviewer access or a failed/rate-limited review is an access blocker, not a pass; report it without posting duplicate requests.
- When Codex completes, assess all findings against current code and the declared environment/trust model. Fix every valid, in-scope P1/P2 in that run, with regression coverage and focused verification. Fix P3 only when small, low-risk, and within scope; document other P3 deferrals. P0 is an immediate blocker requiring owner attention. Explain irrelevant, duplicate, already-fixed, or accepted-limit findings in their original threads with evidence; do not silently dismiss genuine issues, expand the trust model, or invent accepted limitations.
- Commit fixes as new commits, push to the same PR, reply with commit/test evidence, resolve addressed threads where permitted, then request one new Codex review for the new head. Repeat the 10-minute initial wait and 5-minute polling for each round until the exact current head has completed review with no actionable in-scope P1/P2 and no selected P3 left. Document any remaining irrelevant/accepted findings and deferred P3s; leave disputed or unfinished threads open. If only dispositions changed and no code changed, do not request an identical review merely to repeat it.
- The developer actively fixes findings, rather than only notifying or queuing them for another tick, within the owner's authorized implementation scope. Ask only for a material scope/design choice, unsafe action, access blocker, or repeated-fix failure. Remain quiet for pending/unchanged polls and ordinary successful iterations; notify on completion, failure, or required owner decision. On completion report head SHA, verification/CI status, and remaining dispositions, and disable that PR's monitor. Also disable it if the PR closes or merges. Do not merge, change protections, or dismiss a blocking verdict without the appropriate owner authorization.

## Communication
- Use one environment-neutral project Slack channel named by `slack_channel_name`. Send authorized posts as Agent Alert through the available Slack plugin or connector, prefixed with `[agentic_env][role]`, such as `[codex][Developer]` or `[cline][Staff Engineer]`. Identify the actual running environment; clarify if unknown, never infer it from the enabled-environments list.
- Never guess a channel. If the configured channel is missing, ask the owner before creating it. If Slack access or channel details are unavailable, record the setup action in `INSTALL-FOLLOWUP.md` and continue independent work. Configuration changes do not create or rename channels; Slack setup never blocks development.
- Continue through the authorized scope without requesting routine confirmation. Commit each completed task after focused verification, then continue to the next task within that scope. Open a PR when the authorized epic is complete.
- A passing test, a commit, or a completed task is progress evidence—not completion of the authorized scope. After each such step, reconcile the canonical task record and immediately begin its next unfinished, authorized task. Do not end a run with a status-only response; progress updates belong in commentary/heartbeats and must be followed by work. If no next task is recorded while scope remains, record one concrete next action before ending. This is an agent behavior rule, not a response-delivery lock: when the host lets an agent emit a final response directly, repository instructions and task-state checks can only audit violations. Genuine prevention requires a host-owned final-submission operation that reads active task state and rejects delivery while work remains.
- End the turn only when the authorized scope is complete or progress requires owner guidance, authorization, or resolution of a blocker. Continue independent work while blocked work waits. Progress updates do not require a response; task completion and commits are not stop points within an authorized epic.
- Do not build a Slack control plane.

## Owner Override and circuit breaker
- Overrides belong only to the current project. Honor Dennis's project-specific chat/Slack override first, then `OWNER_OVERRIDE` in that project's root `.owner-override`. Never read overrides from home directories, parent directories, environment variables, other projects, or shared files/symlinks; never carry an override into another project. File existence alone activates nothing.
- Read dotenv-style `OWNER_OVERRIDE=pause,bypass-review`: trim whitespace, allow matching quotes, ignore blank lines and # comments outside quotes, and use the last assignment per file. An empty value disables file-based overrides; legacy standalone mode lines remain supported when no key exists. Read as data, never source or expand variables. A bare spoken override pauses gating pending clarification.
- `pause`: stop gating and process work; just do the task.
- `bypass-review`: merge without reviewers.
- `reset`: discard in-flight plan and epic state, start fresh, and never replay prior approvals; preserve implementation work.
- No script, reviewer, validator, or host admin may validate, approve, authorize, or block an override.
- Overrides skip; never fake. Record `Owner-Override: <mode>` and a timestamp in the commit trailer or PR description; never call skipped checks passed.
- Dennis may edit AGENTS.md, config, and policy directly at any time without review or approval; no governance rule may gate its own repair.
- Stop and post ONE ranked Choose if the same fix fails three times, process-artifact work exceeds deliverable work, or approval is needed to repair approvals. The intentional two-stage review loop is not limited to two review rounds; routine fix/review iterations and scheduled waits do not trigger this circuit breaker.
- Rank choices: 1. bypass and finish; 2. simplify the rule; 3. continue. Do not run a new approval process for the choice.
